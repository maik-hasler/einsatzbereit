== 4. Geocoding and Geographic Search Strategy

=== Status
Accepted

=== Date
2026-05-13

=== Context
Radius/bounding-box search for volunteer opportunities requires each on-site
opportunity to have geographic coordinates and the read query to support
spatial filtering; the opportunity-detail page's single-marker map also
depends on those persisted coordinates. We need to decide where geocoding
runs and how spatial filtering is implemented in PostgreSQL.

=== Decision
Geocode addresses synchronously in the `CreateVolunteerOpportunity` /
`UpdateVolunteerOpportunity` application command handlers via an
`IGeocodingService` abstraction backed by OpenStreetMap Nominatim, and persist
the coordinates on the `Address` value object. Reads never geocode. Spatial
filtering uses a SQL bounding-box prefilter plus an in-memory Haversine
refinement for radius queries. We do not adopt PostGIS.

=== Rationale
* Geocoding once at write time keeps reads fast and deterministic, and avoids hammering Nominatim on every list request.
* A bounding-box filter on plain nullable `address_latitude` / `address_longitude` columns (no dedicated spatial index) is sufficient for the platform's expected dataset size; results are paginated regardless.
* Haversine refinement happens in memory only on the bbox-bounded candidate set, which is small by construction.
* Nominatim has no API key, is free, and aligns with the project's open-source self-hosting principle. The HTTP client is throttled to one request per second per the public usage policy, with a short request timeout so unreachable hosts do not stall command handlers.

=== Considered Alternatives

==== PostGIS with NetTopologySuite
PostgreSQL extension for proper spatial types and indexes.

* Pros
** True geodesic accuracy and GiST/SP-GiST spatial indexes
** First-class spatial operators directly in EF Core via NetTopologySuite
* Cons
** Requires a Postgres extension to be enabled in every environment (dev via Aspire, Testcontainers in CI, and any other runtime)
** Additional EF Core package (`Npgsql.EntityFrameworkCore.PostgreSQL.NetTopologySuite`)
** Operational complexity and migration noise not justified at current scale

==== Geocode on read (lazy)
Geocode each opportunity on demand when a list request needs coordinates.

* Pros
** No write-time dependency on the geocoder
* Cons
** Every read triggers external network I/O - slow and rate-limit-prone
** Negates the point of caching coordinates

==== Domain event + background geocoder
Raise `OpportunityCreated`, handle it asynchronously, update coordinates later.

* Pros
** Write path is unaffected by geocoder availability
* Cons
** Eventual consistency for pin visibility complicates the UX
** Extra moving parts (outbox / worker) not warranted yet

=== Consequences
* On-site opportunities created or updated while Nominatim is unreachable are persisted with null coordinates; they appear in the list but not on the map until a subsequent update succeeds.
* Geocoding adds a per-request latency of up to one second plus network round-trip on create/update; acceptable for a low-write workload.
* If the platform scales or expands beyond Germany, or dense geographic filtering becomes a hotspot, record the scaling risk as a TDR and, if triggered, capture the PostGIS adoption in a new ADR that supersedes this one.
