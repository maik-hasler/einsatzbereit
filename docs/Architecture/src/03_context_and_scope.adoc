.External Interfaces
[cols="1,2,2", options="header"]
|===
|Interface |Direction |Description

|Browser → Frontend
|Inbound
|Users access the platform via a modern web browser. The frontend is a React SPA served as static assets.

|Frontend → Backend API
|Outbound
|The SPA communicates with the backend via a versioned REST API over HTTPS. Authenticated requests carry a JWT Bearer token; public browsing (opportunity search and detail views) is anonymous.

|Frontend → Keycloak
|Outbound
|Authentication is handled via OIDC Authorization Code Flow with PKCE. The frontend redirects to Keycloak for login and receives tokens upon success.

|Backend → Keycloak
|Outbound
|The backend validates incoming JWT tokens by checking signatures against Keycloak's public JWKS endpoint.

|Backend → PostgreSQL
|Outbound
|The backend persists structured application data (volunteer opportunities, organizations, engagements) in PostgreSQL via EF Core. Binary assets are stored in object storage, not the database.

|Backend → Nominatim (OpenStreetMap)
|Outbound
|The backend geocodes opportunity addresses via the public OpenStreetMap Nominatim service, throttled to about one request per second. The frontend additionally calls it for city autocomplete and loads OSM map tiles. See ADR-4.

|Backend → SMTP mail server
|Outbound
|The backend sends notification and reminder emails via SMTP (Mailpit locally, a real SMTP server in production).

|Backend → Object storage (MinIO / S3)
|Outbound
|The backend stores binary assets (organization logos, user avatars, opportunity banners) in S3-compatible object storage.

|GitHub Actions → GHCR
|Outbound
|On a version tag (`vX.Y.Z` or `vX.Y.Z-rc.N`), CI builds Docker images and publishes them to GitHub Container Registry; RC tags additionally deploy to staging.
|===

.Mapping: Business Interface → Technical Interface
[cols="1,2" options="header"]
|===
|Business Interaction |Technical Realization

|Volunteer searches for opportunities
|`GET /v1/volunteer-opportunities` with optional filter parameters (public, anonymous)

|Volunteer signs up for an opportunity
|`POST /v1/volunteer-opportunities/{id}/engagements`, authenticated via JWT (requires `user` role)

|Organizer creates a volunteer opportunity
|`POST /v1/volunteer-opportunities` with opportunity data, requires `organisator` role in JWT

|Organizer manages their opportunities
|`GET /v1/volunteer-opportunities/{id}` is public; `PUT` and `DELETE` require the `organisator` role
|===
