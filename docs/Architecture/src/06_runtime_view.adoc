== Runtime View

The following three scenarios cover the platform's most representative flows across the two primary personas: signing in, browsing opportunities (the main volunteer read path), and creating an opportunity (the main organizer write path).

=== User Login (OIDC Authorization Code Flow)

A volunteer or organizer opens the application and authenticates via Keycloak using the OIDC Authorization Code Flow with PKCE.

.Runtime: User Login
[plantuml, "runtime-login", png]
....
include::../images/runtime-login.puml[]
....

Key aspects of this flow:

* The frontend never handles passwords - authentication is fully delegated to Keycloak.
* PKCE prevents authorization code interception attacks in the public client (SPA).
* Tokens are persisted in `localStorage` via the OIDC client's `WebStorageStateStore`, so a page reload keeps the session (and end-to-end tests can capture it).
* The access token is a short-lived JWT; the refresh token is used to obtain new access tokens silently.

=== Browse Volunteer Opportunities

A volunteer opens the opportunities page. The frontend fetches the list from the backend API, which queries PostgreSQL. Browsing opportunities is a public, anonymous read - no token is required.

.Runtime: Browse Volunteer Opportunities
[plantuml, "runtime-browse", png]
....
include::../images/runtime-browse.puml[]
....

Key aspects:

* Browsing opportunities is public: the list and detail endpoints allow anonymous access, so no token is required for this flow.
* Authenticated endpoints (for example creating an opportunity or signing up) validate the JWT signature using Keycloak's public JWKS keys, cached locally.
* No session state is held server-side - the backend is stateless.

=== Create Volunteer Opportunity

An organizer fills out the opportunity form and submits it. The backend validates the JWT, checks the `organisator` role, geocodes the address, and persists the new opportunity.

.Runtime: Create Volunteer Opportunity
[plantuml, "runtime-create", png]
....
include::../images/runtime-create.puml[]
....

Key aspects:

* Role authorization (`organisator`) is enforced declaratively at the endpoint; the command handler additionally verifies that the caller organizes the target organization.
* Request-payload validation happens in the API endpoint before the command is dispatched via `ISender`; the handler then enforces domain invariants.
* For on-site opportunities the handler geocodes the address synchronously via Nominatim (see ADR-4); if Nominatim is unreachable the opportunity is still saved, without coordinates, and appears in the list but not on the map.
* The response includes the created opportunity's ID so the frontend can redirect to the detail page.
