== 2. Slow CI Pipeline

- *Author:* @maik-hasler
- *Version:* identified in v1.0.0
- *Date:* 2026-07-18
- *Status:* In Progress

=== Description

The backend CI workflow (`.github/workflows/dotnet.yml`) is the slowest quality gate on the project. It runs on every pull request and every push to `main` that touches `backend/**`, `frontend/**`, or `keycloak/**`, and it must pass before a change can be merged or released. The workflow builds the backend and then runs four test projects sequentially in a single job; the two that boot the full Aspire stack under Docker - `IntegrationTests` and especially `VisualTests` (TUnit.Playwright) - dominate its runtime.

The debt is not that the pipeline is unacceptably slow today, but that its runtime grows steadily and is concentrated in a single, ever-expanding job with no mechanism to keep it bounded. Left unmanaged, feedback latency keeps rising as the `VisualTests` suite grows.

*Trend:* the same workflow measured ~4.5 min in late May 2026, ~5-6 min in mid-June, and ~8-10 min in July - it has roughly doubled in about two months as end-to-end coverage grew.

=== Impact

==== Technical Impact

- *Developer feedback loop:* Every pull request and push waits ~10 minutes for the backend gate before it is known green; release candidates wait on `publish.yml` (~12 min) for the same suite. This is the single largest source of iteration latency.
- *Suite scalability:* All four test projects run sequentially in one job with no sharding or parallelism, so runtime grows linearly with every new `VisualTests` scenario - the suite cannot be extended without directly extending the critical path.
- *Maintainability:* Because `VisualTests` boots the full Aspire stack under Docker, a slow or flaky run is expensive to reproduce and diagnose, and any re-run costs the full ~10 minutes.

==== Business Impact

- *Cost control:* Longer runs consume more GitHub Actions minutes per pull request - relevant for a non-profit, volunteer-driven project with a minimal budget. Any parallelization that adds runners trades wall-clock time for total compute minutes.
- *Contributor experience:* Slow feedback raises the barrier to casual weekend contributions (persona Contributor Caro), working against the project's low-entry-barrier goal.

=== Symptoms

- *Dominant single step:* One step (`VisualTests`) consumes the majority of every backend CI run.
- *Rising duration over time:* Median run time roughly doubled over two months with no infrastructure change.
- *Full re-run cost:* A single flaky end-to-end assertion forces a complete ~10 minute re-run.
- *Stale documentation:* Earlier docs quoted a "20-30 minute" runtime that no longer reflected reality, a sign that pipeline cost was not being tracked.

=== Severity

Low to Medium.

The absolute runtime (~10 min) is currently tolerable and well below the point of blocking work. The debt is the trajectory and structure: a single, unbounded, sequential job dominated by one test project, growing steadily. Severity rises toward High as the `VisualTests` suite expands or if the project opens up to more contributors who each feel the feedback latency.

=== Proposed Solution

Ordered from cheapest quick win to larger strategic change. The project's Appropriateness and minimal-maintenance goals argue for stopping at the first options that keep runtime bounded.

Quick wins (low effort, low risk):

- *Keep the fast checks first:* `Application.UnitTests` and `ArchitectureTests` (~3 s each) already give near-instant feedback and run before the expensive Docker steps; keep that ordering so obvious failures fail fast.
- *Confirm caching is effective:* NuGet (`actions/cache`) and pnpm (`setup-node` cache) are already configured. Verify cache hit rates in the logs; the setup phase (~60 s) is already small, so there is little further to gain - do not over-invest here.
- *Skip Docker layer caching:* Image pull is only ~13 s (pre-pull step), so Docker layer caching is not worth the added workflow complexity at current numbers.

Structural (medium effort):

- *Split the two Aspire test projects into parallel jobs:* Run `IntegrationTests` and `VisualTests` as separate jobs so their wall-clock overlaps instead of summing. The critical path drops from ~10 min to roughly ~8 min (the longer job plus setup), at the cost of roughly doubled compute minutes and a duplicated build per job (mitigate by sharing the build output as an artifact).

[NOTE]
====
*Eliminated the actual repeated-download source instead of centralizing the build (2026-07-28):*

- *Root-caused "gateway errors from downloading images repeatedly" against real CI logs* rather than assuming the three `docker pull` calls in "Pre-pull Docker images" were the cause - across several recent runs (both success and failure) that step consistently completed in ~10-15s with no errors. The actual repeated large download was `tests/VisualTests.csproj`'s `InstallPlaywrightBrowsers` MSBuild target (`AfterTargets="Build"`), which fetches Chrome for Testing + Chrome Headless Shell (~290 MiB combined) from `cdn.playwright.dev`. Because `integration-tests` and `visual-tests` both ran `dotnet build` against the whole `Einsatzbereit.slnx`, `integration-tests` was compiling (and therefore triggering the Playwright install for) `VisualTests.csproj` despite `IntegrationTests` never referencing it or using a browser - a pure wasted ~290 MiB download on every single run, on top of `visual-tests`' own (legitimate but also uncached) copy of the same download.
- *Fix:* scoped every test job's restore/build to just its own project (`dotnet restore tests/<Project>` / `dotnet build tests/<Project> --no-restore`) instead of the whole solution - `integration-tests` never touches `VisualTests.csproj` now, so it no longer pays that download at all. `visual-tests` additionally caches `~/.cache/ms-playwright` via `actions/cache` (keyed on `Directory.Packages.props`, matching the existing NuGet cache key convention), so the download that remains legitimate only happens once per Playwright version rather than on every run. Applied to both `dotnet.yml` and `publish.yml`.
- *Initially proposed scoping each job's build down instead of a single upstream `build` job whose artifact every test job downloads*, reasoning that `dotnet restore` is already cache-backed and cheap (the actual redundant network cost was the Playwright download above, not restore or the Docker pulls) and that a shared build crossing jobs via `actions/upload-artifact`/`download-artifact` would serialize setup+build (~2 min) *before* any test job starts, instead of today's model where each job's setup+build overlaps with the others in parallel - trading a faster critical path for fewer total compute-minutes, the wrong side of this project's stated trade-off (public-repo compute is free; wall-clock feedback latency is not - see the Business Impact section above).
- *Overridden on explicit request: adopted the single-`build`-job/artifact-fan-out shape anyway.* The repo owner weighed the wall-clock trade-off above and asked for it regardless - `dotnet.yml` now has one `build` job (`dotnet restore` + `dotnet build` for the whole `Einsatzbereit.slnx`) that `fast-tests`/`integration-tests`/`visual-tests` all depend on (`needs: build`) and consume via `actions/upload-artifact`/`download-artifact` (`publish.yml` mirrors this with `backend-build`). `format-check` stays independent (it never needed a build, only a restore, and is the one job that would lose the most by waiting). Two things confirmed empirically before shipping this, not assumed: (1) `dotnet run --project X --no-restore --no-build` still needs `~/.nuget/packages` physically present even with the artifact's `bin`/`obj` restored - without it, MSBuild project evaluation fails outright (`OutputType is 'Library'` instead of the test-SDK-contributed `Exe`) because it can't import the `.props`/`.targets` files packages contribute - so every downstream job still restores the same `actions/cache` NuGet key `build` populated, just never runs `dotnet restore` itself; (2) the artifact is genuinely large - the whole solution's `bin`/`obj` output measured ~567 MiB uncompressed / ~218 MiB zipped locally (each test project carries its own copy of shared framework dependencies like `TUnit`/`Aspire.Hosting.Testing`), so this trades some upload/download time on every run for one restore+build instead of three. Re-measure wall-clock once this has run for real; if the artifact-transfer cost turns out to dominate, sharding (below) is the next lever to reach for instead of reverting this.
- *`VisualTests` parallel-limit tightened for flakiness, not speed:* `VisualTestsParallelLimit` (`AssemblyParallelLimit.cs`) capped concurrent tests at `Environment.ProcessorCount`, which leaves zero spare CPU for the Aspire-hosted stack itself (backend/Postgres/Keycloak/frontend) once that many Chromium+axe-core tests are running - a plausible structural cause of the recurring "tips over the timeout" pattern already called out in `AuthHelper.GoToOrgAppDashboardAsync`'s comment (most recently: two `AccessibilityTests` methods timed out on the same `GET /v1/organizations` round trip in the same 2026-07-28 run). Changed to `Environment.ProcessorCount - 1` (minimum 1) to reserve one core for the stack. This is a structural mitigation, not a fix confirmed by controlled experiment - Docker/Aspire can't be run in a sandboxed session to load-test it locally, so treat it as a hypothesis to re-evaluate against real CI failure rates over the following runs; if flakiness persists, sharding (below) is the next lever, now for reliability as well as speed.
- *Found a second, distinct flake live on this change's own PR run:* `HomePage_HasNoSeriousA11yViolations` failed on a `color-contrast` violation against `text-brand-200` stats-row labels, which sit inside `global.css`'s `.animate-fade-up-d4` entrance animation (opacity 0 -> 1, staggered ~0.5s delay). Axe-core is deterministic given the DOM it's handed, so this was not the CPU-contention timing pattern above - it was a race between the scan and a still-fading element being caught at partial opacity, reading a lower (alpha-blended) contrast than the settled UI ever shows. Fixed at the source rather than in the one page it happened to surface on: `VisualTestBase` now overrides `ContextOptions` to set `ReducedMotion = ReducedMotion.Reduce`, which skips `global.css`'s `@media (prefers-reduced-motion: no-preference)`-gated animations entirely for every `VisualTests` browser context - the same rendering a real reduced-motion user gets, and immune to this race by construction rather than by timing the scan around it.
====
- *Shard `VisualTests`:* Split the Playwright suite across N parallel shards, each on its own Aspire stack. This is the only lever that scales sub-linearly as the suite grows, but each shard multiplies Docker and compute cost - adopt only once a single `VisualTests` job is the clear blocker. Not warranted yet: even the slowest job today (`visual-tests`, ~6 min) is well short of being the pipeline's own blocker, consistent with this document's policy of stopping at the first option that keeps runtime bounded.

Strategic (larger change, defer until justified):

- *Move end-to-end tests off the per-PR critical path:* Keep build, unit, architecture, and integration tests on every pull request (fast and deterministic) and run the full `VisualTests` suite on a merge queue or nightly schedule instead of every push. This is the largest feedback-time win and best fits the Maintainability goal, at the cost of slightly later end-to-end signal.
- *Larger or self-hosted runners:* GitHub-hosted larger runners are paid (conflicts with the minimal-budget constraint); a self-hosted runner fits the self-hosting principle (ADR-3 rationale) but adds operational burden that the single-maintainer constraint discourages. Revisit only if the suite outgrows the hosted two-core runner.

=== Consequences of Delay

Deferring is acceptable in the short term - the pipeline is not yet a hard blocker. However:

- Runtime keeps climbing with each new end-to-end scenario, and the fix becomes more disruptive the larger the single job grows.
- Contributor feedback latency erodes the low-entry-barrier goal precisely as the project tries to attract more contributors.
- The gap between documented ("20-30 min") and actual (~10 min) runtime showed that pipeline cost was going untracked; without a tracked budget, regressions go unnoticed until they hurt.

=== Dependencies

- *Test isolation:* Sharding or parallelizing depends on `VisualTests` scenarios being independent and safe to run against separate Aspire stacks.
- *Budget:* Any option that adds runners or minutes depends on the project's tolerance for additional GitHub Actions cost.
