== 2. Slow CI Pipeline

- *Author:* @maik-hasler
- *Version:* identified in v1.0.0
- *Date:* 2026-07-18
- *Status:* In Progress

=== Description

The backend CI workflow (`.github/workflows/dotnet.yml`) is the slowest quality gate on the project. It runs on every pull request and every push to `main` that touches `backend/**`, `frontend/**`, or `keycloak/**`, and it must pass before a change can be merged or released. The workflow builds the backend and then runs four test projects sequentially in a single job; the two that boot the full Aspire stack under Docker - `IntegrationTests` and especially `VisualTests` (TUnit.Playwright) - dominate its runtime.

The debt is not that the pipeline is unacceptably slow today, but that its runtime grows steadily and is concentrated in a single, ever-expanding job with no mechanism to keep it bounded. Left unmanaged, feedback latency keeps rising as the `VisualTests` suite grows.

=== Impact

==== Technical Impact

- *Developer feedback loop:* Every pull request and push waits ~10 minutes for the backend gate before it is known green; release candidates wait on `publish.yml` (~12 min) for the same suite. This is the single largest source of iteration latency.
- *Suite scalability:* All four test projects run sequentially in one job with no sharding or parallelism, so runtime grows linearly with every new `VisualTests` scenario - the suite cannot be extended without directly extending the critical path.
- *Maintainability:* Because `VisualTests` boots the full Aspire stack under Docker, a slow or flaky run is expensive to reproduce and diagnose, and any re-run costs the full ~10 minutes.

==== Business Impact

- *Cost control:* Longer runs consume more GitHub Actions minutes per pull request - relevant for a non-profit, volunteer-driven project with a minimal budget. Any parallelization that adds runners trades wall-clock time for total compute minutes.
- *Contributor experience:* Slow feedback raises the barrier to casual weekend contributions (persona Contributor Caro), working against the project's low-entry-barrier goal.

=== Symptoms

- *Dominant single step:* One step (`VisualTests`) consumes the majority of every backend CI run.
- *Rising duration over time:* Median run time roughly doubled over two months with no infrastructure change.
- *Full re-run cost:* A single flaky end-to-end assertion forces a complete ~10 minute re-run.
- *Stale documentation:* Earlier docs quoted a "20-30 minute" runtime that no longer reflected reality, a sign that pipeline cost was not being tracked.

=== Severity

Low to Medium.

The absolute runtime (~10 min) is currently tolerable and well below the point of blocking work. The debt is the trajectory and structure: a single, unbounded, sequential job dominated by one test project, growing steadily. Severity rises toward High as the `VisualTests` suite expands or if the project opens up to more contributors who each feel the feedback latency.

=== Proposed Solution

Ordered from cheapest quick win to larger strategic change. The project's Appropriateness and minimal-maintenance goals argue for stopping at the first options that keep runtime bounded.

Quick wins (low effort, low risk):

- *Keep the fast checks first:* `Application.UnitTests` and `ArchitectureTests` (~3 s each) already give near-instant feedback and run before the expensive Docker steps; keep that ordering so obvious failures fail fast.
- *Confirm caching is effective:* NuGet (`actions/cache`) and pnpm (`setup-node` cache) are already configured. Verify cache hit rates in the logs; the setup phase (~60 s) is already small, so there is little further to gain - do not over-invest here.
- *Skip Docker layer caching:* Image pull is only ~13 s (pre-pull step), so Docker layer caching is not worth the added workflow complexity at current numbers.

Structural (medium effort):

- *Split the two Aspire test projects into parallel jobs:* Run `IntegrationTests` and `VisualTests` as separate jobs so their wall-clock overlaps instead of summing. The critical path drops from ~10 min to roughly ~8 min (the longer job plus setup), at the cost of roughly doubled compute minutes and a duplicated build per job (mitigate by sharing the build output as an artifact).
+
[NOTE]
====
*Implemented (issue #773):*

- *`dotnet.yml` split into 3 parallel jobs:* `fast-tests` (`Application.UnitTests` + `ArchitectureTests`, scoped so it skips `VisualTests`' Playwright install), `integration-tests`, `visual-tests`. No `needs` between them.
- *Housekeeping:* added a `concurrency` group (cancels superseded runs on the same PR), added `timeout-minutes` to every job (there was none before - a hang would have run the full 360-minute default), and added the NuGet `actions/cache` step `publish.yml` was missing.
- *Cost: $0.* Public repo, plain `ubuntu-latest`, nowhere near the ~20 concurrent-job cap.
- *`VisualTests` login cost cut:* 78 of 117 tests only needed a login as setup. `AuthHelper.FastSignInAsync` mints a token directly (same mechanism `IntegrationTestFixture` already used) and seeds it into browser storage instead of driving the login UI. Two logins stay real on purpose - `JwtAudienceTests` and a new round-trip test in `AuthGuardTests` - so the actual login flow and the frontend/frontend-test mapper parity the fast path relies on stay under real coverage.
- *First real run (2026-07-19, n=1):* `format-check` ~1 min, `fast-tests` ~1 min, `integration-tests` ~4 min, `visual-tests` ~6 min, all parallel → critical path ~6 min. Down from ~9.6 min, better than the ~8 min estimate above (that estimate predated the login-cost fix). Preliminary - re-measure at n=20+ before treating 6 min as the new baseline.
- *`publish.yml` got the same split* (`backend-fast-tests`/`backend-integration-tests`/`backend-visual-tests` → `publish-backend`), since this project cuts an RC per bug fix/feature (not just on releases), so it runs often enough to matter. `publish-backend` keeps its job id for `deploy-staging`'s reference, now just version-extract → GHCR login → build → push, gated on all three test jobs. Not yet observed on a real tag push.
====
- *Shard `VisualTests`:* Split the Playwright suite across N parallel shards, each on its own Aspire stack. This is the only lever that scales sub-linearly as the suite grows, but each shard multiplies Docker and compute cost - adopt only once a single `VisualTests` job is the clear blocker. Not warranted yet: even the slowest job today (`visual-tests`, ~6 min) is well short of being the pipeline's own blocker, consistent with this document's policy of stopping at the first option that keeps runtime bounded.

Strategic (larger change, defer until justified):

- *Move end-to-end tests off the per-PR critical path:* Keep build, unit, architecture, and integration tests on every pull request (fast and deterministic) and run the full `VisualTests` suite on a merge queue or nightly schedule instead of every push. This is the largest feedback-time win and best fits the Maintainability goal, at the cost of slightly later end-to-end signal.
- *Larger or self-hosted runners:* GitHub-hosted larger runners are paid (conflicts with the minimal-budget constraint); a self-hosted runner fits the self-hosting principle (ADR-3 rationale) but adds operational burden that the single-maintainer constraint discourages. Revisit only if the suite outgrows the hosted two-core runner.

=== Consequences of Delay

Deferring is acceptable in the short term - the pipeline is not yet a hard blocker. However:

- Runtime keeps climbing with each new end-to-end scenario, and the fix becomes more disruptive the larger the single job grows.
- Contributor feedback latency erodes the low-entry-barrier goal precisely as the project tries to attract more contributors.
- The gap between documented ("20-30 min") and actual (~10 min) runtime showed that pipeline cost was going untracked; without a tracked budget, regressions go unnoticed until they hurt.

=== Dependencies

- *Test isolation:* Sharding or parallelizing depends on `VisualTests` scenarios being independent and safe to run against separate Aspire stacks.
- *Budget:* Any option that adds runners or minutes depends on the project's tolerance for additional GitHub Actions cost.
